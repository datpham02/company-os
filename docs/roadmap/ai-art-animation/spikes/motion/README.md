# Motion spike tools (Board R&D, 2026-11-22)

Engine-neutral, standard library + NumPy/Pillow/SciPy (ComfyUI's embedded Python; no new dependency).

| File | Purpose |
|---|---|
| `motion.py` | solver v2 (structure.v2 + motion.v2: FK chains, joint limits, shoulder shift, PCHIP splines with broken-tangent keys, leg IK to contacts, rigid weapon on the hand bone), raw QA measurements (no default thresholds; directional ones in the character frame, so mirrored clips measure the same), evidence renders |
| `motion_v1.py` | solver v1 (method A, arm IK) - kept for the record; its structure.v1 file was superseded by `structure_brute_hammer.json` v2, so A is reproduced from `attack_hammer_v1_A.motion.json` only with the v1 structure from this branch's history of the R&D folder (not kept). |
| `cmu_amc.py` | ASF/AMC reader + 3D forward kinematics |
| `retarget_cmu.py` | method C: projection, retargeting, contact cleanup, hip clamp, KB wrist rule, phase detection → motion.v2 |
| `data/structure_brute_hammer.json` | benchmark structure (measured on the master art) |
| `data/attack_hammer_B.motion.json` | method B |
| `data/map_cmu79_brute.json`, `data/attack_hammer_C.motion.json` | method C map and its derived motion |

**CMU data is not in this repository** (licence: free for all uses, the data may not be resold even converted; we keep
only derived keys). The Board downloads `79.asf`, `79_01.amc`, `80.asf`, `80_71.amc` from mocap.cs.cmu.edu/subjects/
into `refs/cmu/` next to `data/` (decision K1, 2026-11-22) before running method C.

Run (from the folder holding `data/` and `refs/`):
```
python -I -s motion.py data/structure_brute_hammer.json data/attack_hammer_B.motion.json review_B
python -I -s retarget_cmu.py data/map_cmu79_brute.json data/structure_brute_hammer.json data/attack_hammer_C.motion.json
python -I -s motion.py data/structure_brute_hammer.json data/attack_hammer_C.motion.json review_C
```

## Added after the anatomy and universal-motion amendments (2026-11-22)

| File | Purpose |
|---|---|
| `profiles/*.json` | anatomy profiles (`anatomy-profile.v1`): humanoid base (clinical = normative reference values, functional = task observations, both from kb/human_joint_table.json with per-tier provenance; no value is gate-eligible), stylized and heavy humanoid (overrides carry their own heuristic provenance), quadruped, flying, multi-limbed (heuristic design values), custom template |
| `posecheck.py`, `rules.py`, `motion_rules.json` | validation with the Board's result states (KA-BD-5, 2026-11-23): pass / fail / warn / unknown / not_applicable, each with a reason; every unknown also has an `unknown_kind` (invalid_input naming the field, unsupported, unmeasurable). Rules carry scope (action category, entity tags, representation), class and enforcement eligibility; only structural invariants (hierarchy, bone length, attachment, grip, rigidity, reachability, declared contacts, weapon vs floor) can fail. Anatomical ranges on the planar rig are 2D proxies of 3D tables and warn at most. Roles and structural thresholds are owned by the registry (a motion can only tighten them; a mandatory rule becomes advisory only through an approved registry exception). Heavy-strike, heuristic and biomechanics rules are advisory by default. Verdict: mandatory fail -> rejected, mandatory unknown -> blocked. Artistic items stay unknown until a review record bound to the exact revision (motion, structure, validation-profile and artwork hashes, evidence sha256) and a separate governed approval record exist. The motion must declare `category` from the registry vocabulary, the structure its `representation` |
| `poselib.py`, `data/poses_brute.json`, `poses_brute/` | validated pose library (10 poses + 1 negative example). `poselib.py` now uses the same rule engine; the committed `poses_brute/` entries were generated by the previous validator and are not regenerated |
| `tests/test_motion_system.py` | 53 tests, classified in the file's docstring: unit tests (8 solver tests and the rule/registry checks), synthetic regression fixtures (edits of the benchmark data, a synthetic idle on the same hammer humanoid), actual motion benchmarks (B, C and the pose library as committed). No visual review and no production validation; no CI workflow runs the suite (run it locally) |
| `entity/` | Entity Motion Profile schema, component registry (`components.json`), 7 example entities, `entity.py plan` (method selection) |


## Supported scope of the solver and validator (Board code review of PR #110, 2026-11-23)

The solver is an R&D spike validated on **one** structure: the heavy-hammer benchmark humanoid
(`data/structure_brute_hammer.json`). It is not a universal entity solver.

| | Status |
|---|---|
| planar_2d humanoid biped: `trunk` chain (pelvis, chest, ...), legs off `pelvis` planted on contacts with toe/heel, one rigid attachment named `hammer` with points head and butt, profile extending `humanoid_base` | validated (B, C, poses; synthetic idle and walk on the same structure) |
| unarmed, sword or any other attachment name, several attachments | unsupported: `meta.solver_scope` unknown, blocked |
| quadruped, multi-limbed, flying profiles; hovering or legless entities | unsupported: `meta.solver_scope` unknown, blocked |
| `depth_3d` or any representation without a solver | unsupported: `meta.representation` unknown, not solved, blocked |

Unsupported or invalid input is reported before solving (named fields) and the structural rules are then unknown,
never pass or not_applicable. The ground-penetration tolerance (3.0 px) is experimental and specific to the
heavy-hammer benchmark (px of its 832x1216 master canvas); it is not a Studio threshold and awaits Board confirmation.
The floor is the structure's declared contact points (`contacts.<c>.ground_y` is the contact joint's height when
planted, plus the toe/heel y), or `ground.line_y`.
