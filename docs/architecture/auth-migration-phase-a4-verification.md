## 4. Case details

The evidence files are JSON, kept in a folder in the Board Operator's profile, outside the repository. They are redacted:
- tokens are shown as `pcp_<redacted>`;
- emails, passwords and session cookies are never recorded;
- the claim link and CLI approval links appear only in the session conversation, not in these files.

Sandbox user ids are random identifiers, not personal data.

### VA-1: `authenticated` mode and keyless refusal

- **Precondition:** switched to `authenticated` and restarted.
- **The first start was refused.** The control script had written `config.json` with a UTF-8 BOM, and Paperclip's doctor would not start ("Failed to parse JSON"); nothing was written. Fixed by writing UTF-8 without a BOM.
- **Results:**

  | Request (keyless) | Expected | Actual |
  |---|---|---|
  | `GET /health` | 200 | 200 |
  | `GET /companies` | 403 | 403 "Board access required" |
  | `POST /companies` | 403 | 403 "Board access required" |
  | `GET /companies/:id/issues` | 403 | **401 "Unauthorized"** |
  | `GET /issues/:id` | 403 | **404 "Issue not found"** |
  | `PATCH /issues/:id` | 403 | **404 "Issue not found"** |
  | `POST /companies/:id/issues` | 403 | **401 "Unauthorized"** |
  | `GET /admin/users` | 401 | 401 |
  | `POST /admin/users/local-board/demote-instance-admin` | 401 | 401 |

- **Result: PASS.** The plan's failure criterion ("any keyless 2xx except health") was not met. **Deviation:** the issue routes answer 401 or 404 rather than 403. Clients must not rely on 403 to detect a missing login.
- **Evidence:** `VA-1-keyless.json`.

### VA-2: board claim

**Precondition:** before the switch, `GET /api/admin/users` listed `local-board` as the only instance admin.

**Server console:** "BOARD CLAIM REQUIRED … open this one-time URL to claim ownership".

**Action:** the Board Operator signed up with a sandbox account, then opened the claim link while signed in.
- Before the claim, the UI showed "No organization access", as expected.
- The server log shows `POST /board-claim/<token>/claim 200`.

**After the claim:**
- `GET /api/board-claim/<token>` reported `claimed`, with the claimant's user id.
- `/admin/users`: the claimant is `isInstanceAdmin: true`; `local-board` is `false`.
- The claimant is `owner` (active) of the sandbox company.
- `local-board` **keeps its `owner` membership**: the claim removes only its admin role.

**Result: PASS.**

**Observations:**
- The claim token and code appear in the server's request log (INFO), so log files must be treated as sensitive until the claim is used.
- The CLI printed "Update available" at every start, so the update check reached npm despite `updates.checkEnabled: false`.

**Evidence:** `VA-2-00-health-before-claim.json`, `VA-2-01-claim-status.json`, `VA-2-02-roles-after-claim.json`.

### VA-3: Board identity through `/api/cli-auth/me`

**Action:**
1. `paperclipai auth login --no-browser`, with `PAPERCLIP_AUTH_STORE` set to a sandbox file.
2. The Board Operator approved in the browser.
3. `GET /api/cli-auth/me` with the stored key, read by the helper and never printed.

**Result: PASS.**
- HTTP 200.
- `userId` equals the claimant's id.
- The response also carries `isInstanceAdmin`, `memberships`, `companyIds`, `keyId` and `source`.
- A search of the CLI output, the server log and every evidence file found no Board token. The CLI's JSON output contains only the approval URL, which holds the challenge secret, not the key.

**Evidence:** `VA-3-cli-auth-me.json`.

### VA-4: participant update, case (a)

**Action:** `PATCH /issues/:id` with exactly:

**Evidence:** `VA-4-00-before.json`, `VA-4-01-after.json`.

### VA-4c: deduplication trap

**Precondition:** a disposable issue (AVE-4) whose stage has two participants:
- `38063505…` (`local-board`)
- `c18efb4d…` (the claimant)

**Action:** a guarded PATCH that changes `local-board` to the claimant.

**Result: hazard confirmed.**
- HTTP 200.
- The stage now has **one** participant: `38063505…` with the claimant's id.
- The second participant entry (`c18efb4d…`) was removed with no error or warning.

The migration procedure must keep the pre-check that VA-4 used (A2 §3.B step 5).

**Evidence:** `VA-4c.json`.

### VA-7: revoked and forbidden tokens

**Revoked key:**
- **Action:** a disposable named Board key, with a 2-hour expiry, was created with the claimant's key. It answered 200, was revoked with `DELETE /board-api-keys/:id` (200), then used again.
- **Result:** **401 "Agent token did not verify; obtain fresh credentials and retry"**.
- **Note:** an unknown token gets the same 401 and message, so a client cannot tell revoked, expired and wrong keys apart.
- **Not tested:** expiry itself, since keys last 30 days. It goes through the same lookup in source (A1 3.6).

**Viewer write:**
- **Setup:** the Board Operator created a second sandbox account. It was given company access with `PUT /admin/users/:id/company-access`, which assigned **`operator` by default**, then changed to `viewer` with `PATCH /companies/:id/members/:memberId`. It is not an instance admin. Its CLI login was approved from its own browser session.
- **Result:** reading the issue list gives 200. Creating an issue and editing an issue both give **403 "Viewer access is read-only"**; the issue count and title are unchanged.

**Result: PASS.**

**Evidence:** `VA-7a-revoked-token.json`, `VA-7b-00-viewer-setup.json`, `VA-7b-viewer-write.json`.

### VA-8: mode rollback

**Action:** stop the sandbox, set `local_trusted`, start it again.

**Result: PASS.**
- Keyless `GET /companies` and `GET /admin/users` give 200 again.
- `local-board` has `isInstanceAdmin: true` again.
- The claimant still exists and **is still instance admin**.
- Companies, issue list and statuses, and the AVE-1, AVE-2 and AVE-3 policies, states and assignees are identical to the pre-rollback snapshot.
- The AVE-3 decision (`lastDecisionId`) is kept.

**Consequence:** after a rollback the instance has two instance admins. A later switch to `authenticated` shows **no new claim link**, because `local-board` is no longer the only admin. The claimant simply stays admin.

**Evidence:** `VA-8-00-before.json`, `VA-8-01-after.json`.

### VA-9: backup and restore

**Backup:**
- `POST /api/instance/database-backups` (keyless, `local_trusted`) gave 201, `trigger: manual`, a file of 123,988 bytes in the sandbox backup folder, and pruned nothing.
- It works even though automatic backups are off in the config.
- `gzip -t` OK; the dump contains the seed issues and `issue_execution_decisions`.

**Restore: BLOCKED.**
- Paperclip 2026.1023.0 has no user-facing restore command. The CLI offers `db:backup` only.
- Its restore routine (`runDatabaseRestore`, `@paperclipai/db` `backup-lib.js` 919) is called only inside `seedWorktreeDatabase`, which `worktree init` uses to snapshot a running source instance into a new worktree instance (CLI `dist/index.js` 52726-52800). It does not restore an existing backup file.
- Following the brief, no restore was improvised, and the original sandbox was never overwritten.

**Evidence:** `VA-9-00-backup.json`.

## 5. Failures and deviations

1. **VA-1:** the issue routes return 401 or 404 to keyless requests, not 403. This is not a security failure, but it is a difference from the plan.
2. **First start refused** because of a BOM in `config.json`, a defect of the control script. Fixed; no data affected.
3. **Update check:** the CLI contacted npm despite `updates.checkEnabled: false` ("Update available: 2026.1117.0").
4. **Claim token in the server log:** the request log contains the claim URL.
5. **`company-access` defaults to `operator`:** granting company access through the admin route gives more than read access unless the role is changed afterwards.
6. **VA-9 restore blocked** (see above).
7. **Live Postgres stopped uncleanly** when the live process was stopped. It recovered on restart.

No unexpected write or state change occurred in any participant test.
